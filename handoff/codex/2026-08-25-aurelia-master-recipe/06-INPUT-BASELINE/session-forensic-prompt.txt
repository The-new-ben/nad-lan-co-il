# המשך Aurelia — שחזור פורנזי עם חוזה שימור ו־diff מלא

המשך את פרויקט Aurelia, אבל התייחס לעמוד הרוכש הנוכחי כאל אב־טיפוס שאינו מאושר מבחינה מעשית. עבודת ה־SEO, המתכון, סדר העמוד, ה־BOM והצ׳ק־ליסט נשמרת. אין לשנות WordPress, להתקין plugin, לעדכן טיוטה או לגעת באתר החי.

המטרה אינה להמציא חוויה חדשה. המטרה היא לקחת את כל היכולות הטובות שכבר פותחו ב־Rainbow, DO, Dimri Yama, Ashira ובמנוע המשותף של NadLan, להבין אותן ברמת הקוד ולהרכיב מהן את Aurelia בלי לאבד עבודה קיימת.

## חוק עליון: אין החלפה שקטה

אסור למחוק, להחליף, לפשט או לדמות יכולת קיימת בלי להציג זאת במפורש.

אין להחליף:

- Mapbox במפת תמונה;
- אלומה מחושבת באלומת CSS דקורטיבית;
- model-viewer או GLB בפוסטר שמוצג כמודל;
- hotspot המעוגן למודל בנקודת CSS שרירותית;
- סיור POV/360 בתמונה רגילה;
- סטודיו עובד בכפתורים שאינם משנים את התוכנית;
- endpoint חי בטופס מקומי בלבד;
- נתונים קיימים בטקסט שהומצא מחדש.

אם אי אפשר להפעיל יכולת קיימת במעבדה, יש להשאיר את המימוש המקורי בחבילת WordPress, להציג fallback נפרד ומסומן במעבדה, ולהדליק נורה כתומה. אין להציג fallback כאילו הוא שווה למקור.

## שלב 1 — הקפאת קו הבסיס לפני עריכת קוד

לפני שינוי קובץ כלשהו, צור Baseline Package בלתי משתנה הכולל:

1. רשימת כל קובצי JavaScript, CSS, PHP, JSON והנכסים הרלוונטיים.
2. נתיב מלא, גודל ו־SHA-256 של כל קובץ.
3. גרסת source מלאה של:
   - `engine.js`
   - `mapbox-init.js`
   - `studio.js`
   - `buyflow.js`
   - `mv-ux.js`
   - `i18n.js`
   - plugin/adapter של Aurelia
   - template ו־CSS של עמודי הפרויקט
4. snapshot של `window.NADLAN_SHOWROOM` בכל פרויקט.
5. מיפוי שדות WordPress המזינים כל רכיב.
6. HTML source ציבורי אמיתי של כל עמוד, ככל שהגישה מאפשרת.
7. DOM snapshot לאחר הרינדור.
8. צילומי מסך של המצבים המפורטים בהמשך.
9. רשימת event listeners, endpoints, query parameters ו־runtime globals.
10. תיעוד של כל יכולת שאינה מופיעה כרגע במסך אך עדיין קיימת בקוד.

אם source ציבורי אינו נגיש, אל תעקוף מגבלה ואל תנחש. שמור את הבדיקה כתומה וציין בדיוק איזו ראיה חסרה.

## שלב 3 — Capability Regression Ledger

צור מסמך שמציג כל הבדל בין המערכת הקיימת לבין מעבדת Aurelia.

לכל הבדל השתמש באחת הקטגוריות בלבד:

- `RETAINED` — נשמר ללא שינוי;
- `REUSED` — הועתק מהמימוש הקאנוני;
- `WRAPPED` — הקוד המקורי נשמר ונוספה סביבו שכבה;
- `EXTENDED` — נוספה יכולת בלי להסיר את המקור;
- `SIMULATED` — הדגמה מקומית שאינה שקולה למקור;
- `REPLACED` — המקור הוחלף;
- `REMOVED` — היכולת נעלמה;
- `UNKNOWN` — עדיין אין מספיק ראיות.

לכל `SIMULATED`,‏ `REPLACED` או `REMOVED` הצג:

- הקוד המקורי;
- הקוד החדש;
- הסיבה;
- מה אבד;
- ההשפעה על המשתמש;
- ההשפעה על מובייל;
- ההשפעה על SEO/DOM;
- תוכנית השחזור.

אין להתקדם כאשר `REMOVED` אינו מוסבר. ברירת המחדל היא שחזור המקור, לא הצדקת ההסרה.

## שלב 6 — מסלול אנכי ראשון בלבד

לאחר השלמת המיפוי, בנה מחדש מסלול אחד:

בחירת דירה בבניין
→ hotspot אמיתי
→ כרטיס דירה
→ תוכנית מסונכרנת
→ Mapbox אמיתי
→ אלומה לפי azimuth וגובה הקומה
→ מראה מהחלון
→ חזרה לאותה דירה.

### דרישות מחייבות

- hotspot מחובר ל־mesh, ל־hotspot_position או למיפוי חזית/קומה מבוסס נתונים.
- כל הכלים משתמשים באותו `unit_id`.
- `plan_id`, כיוון, קומה, מחיר ו־camera orbit שייכים לאותה יחידה.
- Mapbox משתמש בקואורדינטות הפרויקט הקאנוניות.
- האלומה משתמשת ב־`directionAzimuth`, ב־map bearing ובגובה הקומה.
- מעבר בין סצנות אינו מאפס state.
- במובייל הבניין נשאר גלוי ואינו זז בעת פתיחת הכרטיס.
- אין overlay שמסתיר את אזור הבחירה.
- כל כפתור שמוצג עובד.
- אין תמונה רגילה שמוצגת כמודל, מפה או סיור.
- fallback מוצג כ־fallback במעבדה בלבד ואינו מחליף את קוד WordPress.
- השפה הציבורית היא שפה של רוכש יוקרה, לא שפה של מפתח או צ׳ק־ליסט.

## שני מסלולים נפרדים

שמור תמיד:

### Recipe Lab

הדגמה מקומית לבדיקה חזותית ואינטראקטיבית. אינה משנה WordPress.

### WordPress-compatible

מימוש המבוסס על הקוד, השדות, הסקריפטים וה־endpoints הקיימים. אין לפשט אותו כדי להתאים למעבדה.

שני המסלולים חולקים נתונים ו־IDs, אך קוד ההדגמה אינו רשאי להחליף את קוד הייצור.

## פורמט המסירה

לפני שאתה אומר שהחתך מוכן, מסור:

1. Baseline Package;
2. מטריצת הפרויקטים;
3. Capability Regression Ledger;
4. Visual Regression Board;
5. pixel diff ו־overlays;
6. unified code diffs;
7. runtime/data-contract diff;
8. interaction replay;
9. רשימת נורות ירוקות, צהובות, כתומות ואדומות;
10. ביקורת עצמית;
11. ZIP עם `BEFORE`,‏ `AFTER`,‏ `DIFF`,‏ `EVIDENCE`,‏ `DEMO` ו־`WORDPRESS`.

אל תכתוב “הכול עובד” או “100%” על סמך קיום של רכיב. נורה ירוקה דורשת קליק עובד, state נכון וראיה.

בסיום החתך הראשון, עצור לפני סיור הפנים, המתקנים והסטודיו. הצג לי את ההשוואה באפליקציה ואת הקוד זה לצד זה, כדי שאוכל לראות במפורש מה נשמר, מה הורחב ומה כמעט נמחק.
