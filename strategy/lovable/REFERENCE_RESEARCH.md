# Lovable And Real-Estate Product References

Date: 2026-06-22.

## Lovable Workflow References

1. Lovable best practices: use the knowledge file, plan mode, preview toolbar, and GitHub/version-control wisely.
   - https://docs.lovable.dev/tips-tricks/best-practice

2. Lovable prompting best practices: plan before prompting, map the user journey visually, get the design right first, prompt by component, use real content, and think in systems.
   - https://docs.lovable.dev/prompting/prompting-one

3. Lovable design systems: design systems define reusable components, styles, and setup instructions across projects.
   - https://docs.lovable.dev/features/design-systems

4. Lovable GitHub integration: projects can sync with GitHub, collaborate through branches/PRs, and sync changes back.
   - https://docs.lovable.dev/integrations/github

5. Lovable deployment/ownership: Lovable projects can be synced to GitHub and self-hosted; code and data should remain portable.
   - https://docs.lovable.dev/tips-tricks/deployment-hosting-ownership

## Product Decisions From Research

- Lovable should be used as a component/screen design system, not as hidden memory.
- Prompt by component and journey, not "make the whole site beautiful."
- Project showroom must use official/concept/missing asset states.
- Real apartment selectors use real renders/elevation images or official floor plans with traced zones.
- Interior tour should be a real tour/floor-plan/iframe state or an honest missing state.
- GitHub sync is useful only if every generated change is reviewed in the repo.
