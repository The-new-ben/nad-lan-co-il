# Recipe: build a governed flagship project showroom

Use this repository entry together with the maintained Codex skill
`nadlan-flagship-project-showroom` and the full repository playbook at
`docs/plans/einstein-flagship-recipe-draft/flagship-showroom-recipe-v2-draft.md`.

## The sequence

1. Resolve canonical identity, aliases and collision risk before creating a URL or data record.
2. Build a source register, contradictions ledger and field-level truth states.
3. Select the project archetype and keep one shared, versioned showroom engine.
4. Create one governed per-project package connected to the catalog, WordPress post, model assets,
   payload, content and release manifest.
5. Produce measured HD/LOD/poster assets and governed model anchors. Owner-approved illustration is
   allowed only as non-decision-grade demonstration media.
6. Put the protected 3D stage first. Place View, Interior, Design and Comments as visual invitations
   immediately below it; facilities remain selectable inside Interior unless the shared hierarchy
   is deliberately revised.
7. Support zero inventory without creating pseudo-units, floor-as-apartment controls or false price,
   availability, plan, direction or unit-view claims.
8. Prove the exact package through a password-protected WordPress stage, authenticated readback,
   anonymous non-enumerability, real-browser interaction, fleet regression and rollback.
9. Publish only through the reviewed release workflow. Public release is separate from private-stage
   approval.
10. Promote reusable failures into executable gates and update the shared skill/recipe.

## Model rule

The old `<1 MB, no normals, uint16` rule is retired. Use the recorded fidelity contract. When the
owner requires at least 30,000 triangles, inspect and ship at least 30,000 meaningful rendered
triangles. Normals are required when the viewer lighting path uses them. HD, LOD and poster each
have independent visual, byte, hash and fallback gates. Hidden triangle padding fails.

## Truth and capability rules

- Unknown remains unknown until a newer cited source and reviewed replacement event changes it.
- Exact model coordinates do not imply exact real-world placement.
- Illustrative direction is not calibrated North or a verified view.
- A schematic View is not a live map; a concept Interior is not a spatial unit tour; a draggable
  object is not a plan-aware configurator; prepared-no-write Comments is not OLP delivery.
- Zero inventory is valid. Inventory, price, availability, plan and selected-unit view require their
  own decision-grade contracts.
- Keep the frozen shared beam semantics and run H Infinity, Rainbow, Dimri Yama, Ashira, ToHa2 and
  The Park regression after any shared map/model change.
- Never copy PHP, JavaScript or CSS runtimes into a project package.

## Minimum proof

- Exact identity, source, schema, catalog and asset validation.
- Measured GLB geometry and deterministic asset hashes.
- 320x568, 390x844, 568x320 and 1280x800 real-browser gates, plus keyboard, reduced motion and text
  enlargement checks where applicable.
- No model overlay, semantic clipping, horizontal/inner scrolling, undersized targets, stale history
  state, external tool I/O or accidental writes.
- One visible H1, one global illustration disclosure, private noindex/no-store, authenticated exact
  WordPress readback and anonymous REST/search/sitemap/media denial.
- Side-by-side fleet/competitor comparison, rollback proof and a safe SHA-256-manifested archive.

Repository separation is a later owner decision. Until then, keep one shared engine and governed
per-project packages in this repository; do not create detached project repositories or copied
runtimes.
