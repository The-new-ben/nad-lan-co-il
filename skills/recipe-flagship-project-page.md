## Outcome

Build one buyer product whose canonical identity, evidence, catalog data, content, model, visual
tools, WordPress readback and release state reconcile. Completion requires private WordPress and
real-browser proof; a repository build, fixture, generated payload or local preview is not live
stage proof and never authorizes public release.

## Repository architecture

| Layer | Owner | Rule |
| --- | --- | --- |
| Shared engine target | `plugins/nadlan-config/inc/flagship-surface.php` plus `plugins/nadlan-config/assets/flagship-v3/` | One versioned renderer, viewer, interaction shell and privacy contract for the fleet; the current shared files still encode the Einstein profile described below |
| Archetype recipe | Declared project configuration and acceptance gates | Residential tower, multi-building residential campus, commercial tower or mixed-use compound changes modules and evidence density, never runtime ownership |
| Project package | `data/projects/<project-id>.json` and `assets/projects/<asset-slug>/` | Governed identity, sources, facts, representations, calibration, mappings, experiences and inventory state |
| CMS bridge | Draft payload and publication manifest under `docs/` | Exact private-stage/canonical crosswalk, no copied project runtime and no second canonical |
| Release rail | Repository-native guarded deployment and recovery workflow | Private stage first, exact readback, rollback proof, then a separate confirmed public action |

Einstein is not a single-tower-only shape: its data records one 28-level residential tower, two
13-level boutique residential structures and a two-level commercial base. Its recipe therefore
uses multi-building residential-campus gates plus mixed-use circulation/context checks while the
same flagship engine remains in control.

Implementation boundary at `492d988`: the shared files and governed Einstein package exist, but
archetype is still a documented configuration/acceptance classification, not an executable package
key, selector or provider registry. The current surface is an Einstein-shaped implementation, not
yet a project-neutral engine: client code pins the Einstein experience decision, tool/scene/anchor
cardinalities, `open-frame` styling and Hebrew fallback copy; PHP pins zero-inventory, North,
tool/capability, group/routing and Hebrew-copy rules. These restrictions suit the current Einstein
path but cannot be treated as reusable archetype selection.

Generic-engine acceptance requires all four: trusted package/registry input supplies every
project-specific decision and profile value; the unchanged runtime accepts Einstein and a second
project package with different valid IDs, cardinalities and archetype requirements; cross-project
or mismatched values fail closed; and a shared-runtime scan finds no project-specific slug,
contract/decision ID, scene/style hook, content string or fixed project policy. Until then, call
v3 the current shared surface and do not claim project neutrality.

## Build sequence

1. Resolve the canonical project contract ID, typed structures, parcel/address identity, post ID,
   slug, aliases and collision exclusions.
2. Build the source register, observations, contradictions, expiry/replacement rules and buyer
   fact envelopes. Unknown stays unknown until a newer cited record replaces that field.
3. Select the archetype and required modules. Do not create a detached HTML demo or copy PHP,
   JavaScript or CSS into the project package.
4. Reconcile canonical project JSON, catalog/index membership, the asset package, exact draft
   payload and publication manifest through the immutable project identity.
5. Produce and inspect HD, LOD and poster bytes. Freeze triangles, dimensions, nodes, materials,
   hashes, calibration, model-anchor count and selectable-scene count independently.
6. Put the protected 3D stage first. Render View, Interior, Design and Comments immediately below
   it in normal flow. Facilities remain scenes inside Interior unless the fleet hierarchy changes.
7. Keep zero inventory intentional. Floors, model anchors and concept scenes are not apartments;
   no price, availability, plan, direction or unit view appears without its own decision-grade
   contract.
8. Validate offline and in real browsers, then create or update only a distinct protected stage
   through the guarded workflow. Read back the exact page, meta and asset contracts.
9. Prove anonymous non-enumerability, authorized behavior, recovery, fleet regression and package
   safety. Publishing remains a separate explicit action.
10. Promote reusable failures into executable gates and update the shared skill and this recipe.

## Private-stage and private-asset contract

- Use a distinct password-protected `nadlan_project` linked to the canonical post. Preserve the
  canonical identity in the JSON contract, keep the sandbox catalog `source_id` blank, and retain
  the reviewed source-post crosswalk.
- Before authentication, expose only the password boundary with `noindex`, `noarchive` and
  `no-store`; do not emit project payloads, model URLs or discovery links.
- Anonymous collection, exact ID/slug REST, search, archive, sitemap, feed, oEmbed/embed,
  canonical/discovery and attachment/media probes must not reveal existence, title, slug, post ID,
  dates, taxonomies, body, media or flagship/privacy meta.
- The repository `1.72.206` private-asset source contract makes every rejected binary request a
  terminal 404 with no redirect, a zero-byte body, `Content-Length: 0`, private no-store/no-cache,
  `X-Robots-Tag: noindex, nofollow, noarchive`, `nosniff` and `Referrer-Policy: no-referrer`.
  Authorized responses stream only allow-listed exact bytes and remain private/no-store.
- Treat those statements as source and fixture requirements until an authenticated WordPress run
  proves the same network behavior. Do not describe the stage as live from repository evidence.

## Guarded mutation and recovery

1. Declare `create_only`, `update_exact` or `publish_exact`; publishing always needs separate
   confirmation. Fail closed on an existing object during create-only.
2. Keep artifact spool and rollback backup as sibling directories inside one run-owned root
   directly under `WP_CONTENT_DIR`, disjoint from `WP_CONTENT_DIR/upgrade`, with resolved-scope and
   no-symlink proof.
3. Measure required capacity. If the probe is genuinely unavailable, allow only the recorded
   bounded-unmeasured path below its hard cap; otherwise fail closed.
4. Immediately before install, re-prove scope, archive bytes/entries/expanded bytes, backup
   inventory and exact stage contract. Reconcile a lost response by authenticated exact readback.
5. Snapshot title, content, excerpt, password fingerprint, core post fields and the exact raw-meta
   allow-list. Any drift preserves recovery state and blocks deletion.
6. Roll back a run-created stage before the plugin. Delete it only while ID, slug, ownership
   markers and raw meta still match exactly, then prove both tracked ID and governed scope absent.
7. Before cleanup, re-prove same-run lock ownership. Remove artifact, backup and run root in order,
   persist a durable terminal cleanup marker with absence proof, release the lock, delete state,
   then remove the helper through its separately verified path.
8. An exact already-original state may use the documented zero-copy adoption path only after the
   live plugin, activation, inventory, stage/spool absence and retained-backup contract reconcile.

The current Einstein stage path is stricter: despite the legacy payload label
`create_or_replace_exact_private_sandbox`, its guarded driver implements create-only and aborts if
the exact slug exists. That label does not authorize replacement or update.

## Minimum proof

- Identity, schema, catalog, URL origin, sources, content and exact asset validation.
- Direct GLB inspection for bytes, hashes, triangles, dimensions, materials, nodes, calibration,
  anchor/scene parity and LOD fallback.
- Real Chromium at 320x568, 390x844, 568x320 and 1280x800, plus Hebrew RTL, keyboard, reduced
  motion and effective 200% text.
- One visible H1 and one main; no stage overlay, semantic clipping, horizontal/inner scrolling,
  sub-44px targets, stale history state, duplicate model, console error or external write.
- Exact protected-stage readback; anonymous privacy probes; response-loss reconciliation;
  page-first rollback; run-owned cleanup and recovery evidence.
- Side-by-side fleet/competitor comparison and a safe allow-listed archive with a SHA-256 manifest.

## Repository roadmap boundary

Separate project repositories are a future governance option only. Until the owner approves a
migration plan and shared-engine versioning/release ownership, keep one shared engine and governed
per-project packages in this repository. Do not create detached project repositories, duplicate
runtimes or describe the future split as current architecture.
